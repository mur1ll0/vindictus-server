# Composição interna de UserLogin de laboratório

M13.2d.3a porta a composição recuperada para PostgreSQL e a liga à sessão interna admitida. Não envia mensagens de sucesso ao cliente. O diagnóstico TCP continua recusando login; nenhum aceite de compatibilidade é afirmado.

A sequência é: validar perfil offline explícito → procurar/criar usuário e transferir achievements pendentes → executar lealdade/dormência/recompensas → consultar ban → persistir IP → ler FacebookToken → consultar LimitedAccount → compor os sete campos. O literal PackageCount é **1**, independente da fila. IP NULL vira texto vazio sem eliminar os segundos; IP vazio elimina os segundos. FacebookToken NULL vira vazio; os bytes varchar são decodificados pelo perfil SQL_Latin1_General_CP1/codepage1252, inclusive NUL e os cinco controles sem glifo.

A criação conserva NexonSN signed, nome/case, NextCharacterSN0, ServiceID e ChannelCode0→NULL. Antes do INSERT, cria friend flag1 somente quando a feature está ativa e não há flag. Depois do INSERT, transfere apenas achievements UID=-1 com nome equivalente. Usuários existentes não são sobrescritos, e colisões de ID/nome são recusadas. Uma transação curta serializa as duas chaves; lock/statement timeouts limitam contenção. Ela agrega lealdade inicial/INSERT/ownership atomicamente, uma diferença deliberada das gravações separadas do legado. Não existe comunicação externa durante o lock. O executor existente preserva sua CAS e seus recibos de recompensas; estes recibos não tornam todo o login replayable.

Efeitos anteriores ao ban permanecem gravados quando o login é banido, conforme a ordem real de UserLoginProcessor. Status1 retorna GameUI_Login_Fail_BannedReason_AccountStolen; os outros motivos pertencem ao próprio usuário e obedecem NotifyBanReason. Erros de armazenamento não viram Clear. O erro de persistência de IP que o legado apenas registra é recusado pelo adapter Rust. Não alteramos o adapter antigo de políticas isoladas; o novo fluxo é o caminho da composição completa.

O pacote de conteúdo agora inclui NGM_disable, PassportImmigrator, NotifyBanReason e IPLockTime. A aplicação exige declarações explícitas, NGM_disable ativo e secured=false; profiles parciais/online não são silenciosamente aceitos. PassportImmigrator ativo exige seu serviço ainda não migrado e é recusado antes de SQL. Não concedemos Cheat a partir de IP ou campos do cliente. O perfil do hash/cultura é selecionado explicitamente na admissão existente; nenhuma inferência do host.

A ligação interna verifica o token da tentativa antes de SQL e o deadline absoluto novamente na conclusão, com Drop síncrono que fecha/libera a reserva em cancelamento/erro. Sucesso mantém a reserva até Close/Drop. Não há mudança de conexão TCP ou autoria de usuário HTTP. A operação de banco também possui teto30s, sem renovar o prazo da sessão.

Validação: oracle extrai sem modificar as cláusulas de falha por member, projeção de IP e os sete yields do UserLoginProcessor; stubs independentes apenas para log/journal e entradas sintéticas. Framework x86/x64 executa480cenários e256decodificações por arquitetura. Não é execução do serviço nem oracle de toda a máquina de login. SELECT-only SQL confirma codepage e256valores; efeitos já têm seus oracles anteriores. Integrações novas executam criação/existente, ban com efeitos sem IP, rollback/ownership,8criações concorrentes/um vencedor, colisões, perfis recusados, reserva/reconnect/stale callback e cancelamento sob pool ocupado. Logs completos em .cache/verification; evidência contém hashes/contagens e somente dados sintéticos.

Ainda faltam: adapter TCP→sessão com perfil runtime, tarefa CheckBanType periódica, QueryCharacters e segunda senha/CharacterList; criação com CharacterMaker, template/costume/DefaultItems/skills; SelectCharacter/PlayerService/ItemProxy; canal MMO/Identify/key/partições/posição/movimento. Recompensas enfileiradas não são entrega de inventário. O cliente deve ser executado para validar os contratos alcançados. Migração completa M01–M24 preservada.
