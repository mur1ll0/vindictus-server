# Proveniência das contas de laboratório

M13.3d.2a.1 adiciona uma barreira interna antes de expor o login de laboratório. Nenhum novo listener TCP foi ativado, e o cliente ainda recebe a recusa diagnóstica.

A migração0013 cria game_lab_account_origins, metadado local separado do legado. UID tem PK e FK local indexada para game_users; a exclusão do usuário remove o marcador. Não foi inferida uma relação SQL Server. O marcador contém chave ASCII canônica, fingerprint de32bytes do perfil de operador e data operacional. Nome/payload/fingerprint não têm Debug ou Serialize.

prepare_scoped_lab_user mantém a mesma transação limitada e o lock de identidade de prepare_user. Um usuário existente só prossegue se UID, nome canônico, marcador, fingerprint, ServiceID e ChannelCode conferem. Uma linha sem marcador nunca é adotada; remover seu marcador faz a próxima entrada ser recusada. ChannelCode0 conserva NULL. O caminho interno anterior continua disponível para testes de paridade e importação/provisionamento não cria marcadores.

Para uma identidade nova, os nove conjuntos de dados com UID ou nome são bloqueados e consultados antes de escrever: CharacterInfo, FriendLoyalty, UserAchievements, UserInfo, UserProducts, UserCareInfo, HomeCafeBonus e os dois recibos locais de efeitos/recompensas. Isso protege dados importados sem dbo.User correspondente, inclusive achievement pendente com UID-1. O lock das tabelas é uma barreira local conservadora, limitada a criação de laboratório; não é comportamento recuperado do legado. As escritas de amigo, usuário, marcador e substituição de achievement pertencem à mesma transação. Falhas fazem rollback. Limites de lock2s/statement5s não mudaram.

execute_scoped_lab_user_login e evaluate_scoped_lab_user usam essa barreira antes de recompensas, políticas de banimento e atualização de IP. A recusa fecha a sessão e libera sua reserva; uma nova conexão pode tentar novamente. Fingerprint é contexto confiável de operador, não credencial, passport ou prova de autenticação. Seu cálculo a partir de arquitetura/cultura Framework, hashes originais, serviço e relógio explícito, além de allowlist/configuração privada, é a próxima dependência M13.3d.2a.2. O futuro TCP deve usar somente o caminho scoped.

Seis novos testes PostgreSQL verificam proteção de usuário existente sem alteração de revisão/recibos, oito criadores concorrentes com um vencedor, replay/NULL/perfil/marcador/FK, recusa dos nove donos órfãos e achievement pendente, rollback tardio/readiness, corrida real com um INSERT concorrente não marcado, e reconexão/liberação de reserva na composição de sessão. Os cenários são agrupados em seis testes e executados em schemas descartáveis. O gate completo termina em204Rust/65PostgreSQL/19Python, sem falhas ou avisos.

Docker aplica a migração e preserva os dados anteriores após restart, com zero marcadores no banco real. SQL Server e originais permanecem somente leitura. Logs completos estão em.cache/verification; somente resumos e hashes públicos foram registrados. Não houve push. Próximo: configuração/relógio, TCP/falhas/cleanup/segunda senha/lista e teste manual; depois criação, seleção e MMO/cidade. A migração completa M01–M24 permanece pendente.
