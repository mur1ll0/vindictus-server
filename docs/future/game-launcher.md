## 2. O cliente funciona com arquivos soltos ou exige os `.hfs`?

### 2.1 Evidência

1. **Caminhos de busca:** `.cache/play-client/GameInfo.txt` declara `SearchPaths { Game |gameinfo_path|. ; Game |gameinfo_path|hl2 ; Game ..\source }`. A pasta raiz do cliente é um caminho de busca da engine Source.
2. **Como os pacotes são montados:** strings de `bin/FileSystem_Stdio.dll` (958.224 bytes, só inspeção de strings): `hfs\%s.hfs`, `hfs/%s.hfs`, `Lazy-mounted: %s for %s`, `Loading index file: %s`, `Can't load packfile: %s`, `Incompatible pack file detected!%s`, `target file don't have central dir record!%s`, `use_packfile_to_load_map`, `fs_monitorreadfrompack`. Em `bin/engine.dll` aparecem `Base_platform.hfs`, `Base_hl2.hfs` e `sql/heroes.db3`. Leitura: os `.hfs` são pacotes com diretório central (estilo zip), montados sob demanda ("lazy") a partir de um índice.
3. **Formato do `.hfs`:** em `hfs/286FE9924483F382029EF68BA6C260B3C2563BF9.hfs` (o banco SQLite dentro de HFS citado em `client-compatibility.md`), o cabeçalho é `48 46 01 02` e o fim é `48 46 05 06`. É a estrutura do zip com `PK` trocado por `HF`, método 0 (armazenado), nome de 15 bytes ilegível e conteúdo sem texto claro: nomes e dados ofuscados. As ferramentas do operador em `D:\PROJETOS\VindictusPrivate\Tools` cobrem os dois sentidos: `HFSExtract` (github.com/yretenai/HFSExtract) extrai, e `vZipFlip_HFS` (`unHFS_File.bat` / `ReHFS_File.bat`) converte HFS ↔ zip. Refazer um `.hfs` é, portanto, possível (**hipótese** até repetir com um pacote alterado e o cliente aceitar).
4. **Um pacote por pasta:** são 2.681 `.hfs` na cópia. `hfs_extracted/summary.txt` liga cada nome à pasta que ele contém (`0000AA13… -> models/armor/kingdom`). O nome **não** é o SHA-1 do caminho (testado com `models/armor/kingdom` em minúsculas e maiúsculas). A regra do nome segue desconhecida, e isso pesa para pastas **novas**.
5. **Arquivos soltos já são lidos hoje:**
   - `scaleform/` na raiz tem 453 arquivos soltos (`.gfx`, `.dds`) que não estão nos HFS de scaleform (`hfs_extracted/scaleform` tem 1.475 outros arquivos; `AchievementDialog.gfx` e `ArenaDialog.gfx` só existem soltos). As telas do jogo funcionam, logo são lidas soltas.
   - `sql/heroes.db3` está solto, e o `engine.dll` abre o caminho literal `sql/heroes.db3`. O EndPoint do laboratório só existe nessa cópia solta e foi buscado pelo cliente (`client-compatibility.md:147`), enquanto o banco de dentro do HFS (`hfs_extracted/sqlite/heroes.db3`) traz a URL oficial. Todas as edições de cliente do projeto (lojas, MaxStack, Enhance) já dependem disso.
   - `cfg/` (5 arquivos), `maps/graphs/*.ain`, `sound/`, `media/` também ficam soltos.
6. **Windictus 2023 (somente leitura):** `C:\Windictus 2023` ainda tem 3.596 `.hfs`, mais uma pasta `data/` com 25.484 arquivos soltos (`data/maps/01a.bsp`, `data/models/armor/2016_summer/…mdl`, `data/materials`, `data/scaleform`, `data/scripts`). O `GameInfo.txt` dele tem os mesmos caminhos de busca, sem `data`, e o `FileSystem_Stdio.dll` tem as mesmas strings de HFS. **Hipótese:** o `data/` é montado por binários modificados ou pelo próprio launcher deles. Esse launcher (`Windictus.exe`, .NET, 167.936 bytes) confere a integridade de cada arquivo: o `WindictusLauncherLog.txt` mostra `The following file is corrupted: nexon_api.dll / heroes_text_english_eu.txt / Windictus.exe`. O REA (`inspect_managed_artifact`) não leu os metadados: `Duplicate metadata stream #GUID` é uma proteção anti-descompilação deliberada, e o `VMProtectSDK32.dll` está na pasta.

### 2.2 Como o cliente abre um arquivo (engenharia reversa, 26/10/2026)

Com a autorização do operador, o `bin/FileSystem_Stdio.dll` da cópia (SHA-256 `8b3bf91b6ac1…`) foi analisado no REA (Ghidra 12.1.4). Funções lidas: `CBaseFileSystem::Open` (`0x1000fb10`), busca no índice (`0x10027f30`), montagem sob demanda (`0x10025f00`), leitor do índice (`0x10028990`, `0x100288b0`), hash (`0x10056380`) e abertura em diretório × pacote (`0x1000cee0`).

1. **O índice HFS vem primeiro.** Para leitura, `Open` normaliza o caminho (minúsculas, `\`) e, se o índice estiver carregado, procura nele (`0x10027f30`). Achando, monta o `.hfs` sob demanda (`hfs/%s.hfs`, mensagem `Lazy-mounted: %s for %s`) e abre o arquivo pela posição e pelo tamanho gravados no índice. Só se o caminho **não** estiver no índice, ou se o pacote falhar ao montar, `Open` percorre os caminhos de busca (pastas soltas).
2. **Prefixos bloqueados para soltos.** Se o caminho começa com `mater`, `model`, `scrip` ou `sqlit` (`materials/`, `models/`, `scripts/`, `sqlite/`), a busca de recurso só aceita caminhos de busca que são pacotes (campo `+0x10` do caminho de busca diferente de zero). Ou seja: **modelos, materiais e scripts soltos nunca são lidos**, nem como arquivo novo. Os demais (`scaleform/`, `resource/`, `maps/`, `sound/`, `sql/`, `cfg/`…) podem vir soltos quando não estiverem no índice.
3. **Pacote que falha cai para os soltos.** Se o `.hfs` listado no índice não abre (`Can't load packfile: %s`), o nó é marcado como falho e `Open` segue para os caminhos de busca. É exatamente o que quem montou o 1.69 EN fez: `hfs/RENOMEADo_9FB527B373DCBD159552ADD1710487A724237AF9.hfs` (presente também no original somente leitura) contém `AchievementDialog.gfx`, `ArenaDialog.gfx` e as outras telas do `scaleform/`; renomeado, ele não monta, e o cliente usa as 453 telas soltas da raiz.
4. **Formato do índice** (recuperado e conferido em 26/10/2026; ver 2.4): o arquivo `hfs/E608DF10F284E19AB75FD7D0D8AE9CCF87831041.hfs` tem 14 bytes claros (`48 46 01 02 0a 00` e zeros) e depois um fluxo zlib (`78 da`) cifrado com XOR pela chave de 4 bytes `78 BD 02 47`, aplicada por `posição & 3` (`EncryptedReader` → `InflateReader`, zlib 1.2.3). Descomprimido (2.236.020 bytes), traz um cabeçalho de 0x14 bytes (`HFI`, contagem de pacotes u16 em 0x04 = 2.680, contagem de arquivos u32 em 0x10 = 136.400), uma entrada de 0x14 bytes por pacote (o nome SHA-1 do `.hfs` em 5 u32 little-endian, ordenados) e uma tabela de 16 bytes por arquivo, ordenada pelo hash: hash u32 (`h = 0xAAAAAAAA; h = h*33 + tolower(c)` **só sobre o nome do arquivo**, sem a pasta), primeiro e último caractere em minúsculas, índice do pacote u16, posição e tamanho dos dados dentro do pacote. A pasta é conferida depois, contra o pacote (`0x10027cd0`).
5. **Onde fica o índice:** é o `E608DF10….hfs` (confirmado no cliente, seção 2.4). Ele não aparece no próprio índice, e o HFSExtract não o abre (`CANNOT LOAD`). A escolha do arquivo fica em `.vmp0`, mas a cifra depende só de `posição & 3` (a rotina protegida `0x10028b90` recebe esse valor), o que permitiu achar a chave por força bruta contra o cabeçalho zlib.

### 2.3 Conclusão

- **Comprovado (código):** soltos substituem o conteúdo de um HFS só quando aquele HFS deixa de montar (renomeado ou removido) **e** o caminho não começa por `materials/`, `models/`, `scripts/` ou `sqlite/`. A técnica "desativar o HFS e soltar a pasta inteira" vale para `scaleform/` (já em uso), `resource/` (textos), `maps/`, `sound/` e semelhantes. Ícones novos (`scaleform/item_icon/<nome novo>.tga`) não estão no índice e podem ir soltos sem desativar nada.
- **Comprovado (código):** `scripts/player_costume.txt`, `scripts/item_data.txt`, `models/…` e `materials/…`, sejam alterados ou novos, **só** entram por pacote. Como a posição e o tamanho de cada arquivo estão no índice, refazer um `.hfs` com conteúdo diferente exige **regravar o índice**. O índice já foi localizado, decifrado e recodificado (item 4); o L0-d mostrou que o cliente aceita um índice regravado (seção 2.4).
- **Alternativa por binário:** os `.hfs` `Base_hl2.hfs`/`Base_platform.hfs` são pacotes de caminho de busca (a busca bloqueada os aceita). **Hipótese:** um pacote HF a mais registrado como caminho de busca (o que o Windictus parece fazer com `data/`) passaria nos prefixos bloqueados; exigiria mudar o `GameInfo.txt` ou o binário, e precisa de teste.
- **O motor exige os HFS?** Sim: tudo que está no índice é lido dos pacotes. O launcher distribui os HFS originais como arquivos opacos e acrescenta os soltos; o que for `models/`/`scripts/`/`materials/` vai em pacote.

### 4.1 Evidência: como o cliente faz login (02/11/2026, L-A)

Fontes: cabeçalhos PE (parser Python próprio); `nexon_api.dll` original (SHA-256 `764a7ff5b6f77fa9…`, igual à cópia) aberto no REA (Ghidra 12.1.4); no `Vindictus.exe`, `engine.dll` e `client.dll` originais do 1.69, só desmontagem pontual com Capstone em torno das importações `nxapi_*` e das referências a strings (sem análise do binário inteiro). Logs em `.cache/verification/la/`.

1. **`nexon_api.dll` é só um carregador do Nexon Launcher (NXL).** `nxapi_init(productId)` monta o `CNXAPIContainer`. O `FindNXL` procura o processo `nexon_client.exe` ou `nexon_runtime.exe`, carrega `<pasta dele>\bin\nexon.dll`, chama a exportação `GetDLLInterface()` e usa o objeto devolvido (vtable: +0x3c `InitNXLauncher(productId)`, +0x14 `GetAPI`, +0x1c `GetNXUser`, +0x40 desligar). Sem NXL, `nxapi_init` devolve 0. `nxapi_get_friends` não faz nada. O `nexon.dll` da raiz do cliente é outro arquivo (log4cxx).
2. **O jogo quase não usa esse DLL.** `Vindictus.exe` importa só `nxapi_init`; `engine.dll`, só `nxapi_shutdown`. Ninguém importa `nxapi_get_user` nem `nxapi_get_api`. Logo, a sessão não passa por ele, e um `nexon_api.dll` próprio **não é necessário para o login**. O DLL trocado do Windictus (10,5 MB, libcurl, libcrypto, Discord) deve servir a outras coisas (integridade, presença no Discord): **hipótese**.
3. **Modo de login do `engine.dll`** (função em torno de `0x422f8d80`, campo `+0x98`): `-token <v>` → modo 4; `-mantis` (nome interno do NXL) → modo 3, lê `-passport` e **não** chama o NMCO; só `-passport <v>` → modo 1, `NMManager->[+0xc](passport)` (validação SSO da Nexon) e, na falha, "NMManager - Warning". É o "Erro [Auth] SSO" do T2. Na saída, o mesmo `-mantis` decide chamar `nxapi_shutdown` (`0x421cf737`).
4. **Estado do menu principal no `client.dll`** (`0x385232f0`; não é o caminho do botão Start Game, ver item 7): com `-mantis` devolve o estado `0x29`. Senão, **só se** um dos modos de evento do FeatureMatrix estiver ligado (`E3_Event_2010` ou `Event_PAX_2011_enUS`), lê o passport: com `NGM_disable`, do ConVar **`event_account`** (`0x38e5d9c8`, registrado em `0x38aa5670`, vazio por padrão); sem ele, do NMCO. Passport não vazio → `login->[+8](passport)` e devolve 2, **sem o `LoginDialog_V2`**; vazio ou falha → diálogo. O diálogo também grava o ID digitado no `event_account` (`0x3852245d`); por isso o passport é o ID (B4.2-D).
5. **Os modos de evento não servem como chave:** `E3_Event_2010`/`Event_PAX_2011_enUS` aparecem em 66 pontos do `client.dll`, 5 do `engine.dll` e 9 do `server.dll`. Ligá-los mudaria o jogo inteiro (modo de demonstração).
6. **Outros caminhos vistos:** `-event_account <v>` na linha de comando grava o ConVar, mas também só com um modo de evento ligado (`0x3826ab2a`). O comando `LoginAuto1`/`LoginAuto2` do diálogo lê `ID` e `Password` de um `AutoLogin.txt` (KeyValues, entradas `Auto1`/`Auto2`) e dispara `LoginDialog_OK` (`0x3826a590`): exige o diálogo aberto e um comando de interface.

7. **O Start Game não passa por esse ponto** (LA1 de 02/11/2026: com `+event_account` o diálogo continuou). No 1.69 EU (`LoginDialog_V2` desligado), o Start Game abre o **LoginDialog clássico** (ID, Pass, AUTO1, AUTO2, OK, Cancel, Select Server; captura de tela do operador, 02/11/2026). O tratador dele (`0x3826aad0`) recebe `OnShow` ao abrir: preenche a lista de servidores do EndPointNetwork (cache `0x38e50ea8`), chama `LoginDialog.applyServerName` e `ServerListDialog.selectServerItem` e termina em `0x3826ae0c`. O botão OK manda `Login` (`0x3826ae19`): lê ID, Password e `LoginDialog.Frame_Login.MC_BG.Text_ServerName.text`, grava o servidor nos ConVars `server_name` (`0x38269c70`, `SetValue` em +0x2c) e `server_name_archive` (`0x38e50eb8`), monta o KeyValues `TransitionArgs {ID, Password}` e dispara a transição `LoginDialog_OK` (`0x3851e5f0` → `0x385194d0`, `Transition(nome, args)`, `ret 8`). AUTO1/AUTO2 fazem o mesmo com ID e Password do `AutoLogin.txt` (`0x3826a590`). Com `NGM_disable`, o ID vira o passport (`0x3852245d`) e a senha não sai do cliente. A tela de título `GameTitleMenu_V2` (`ShowLoginDialog`, `0x3826a1d0`) tem a mesma estrutura, mas não é usada com o `LoginDialog_V2` desligado.

**Decisão (L-A, revisada em 02/11/2026):** `scripts/client/patch_client_launcher_login.py` troca o epílogo do `OnShow` do LoginDialog (`0x3826ae0c`) por um salto para a seção nova `.hlgn`. Ali, `CommandLine()->ParmValue("-launcher_ticket", "")`: vazio → o epílogo original, nada muda; com valor → o mesmo que o OK faz, com o ticket como ID e senha vazia; o servidor é o do diálogo ou, se ele ainda não o mostrar, o primeiro do EndPointNetwork (+0x18 contagem, +0x24 nome); sem servidor, o diálogo fica aberto. ### 4.3 Armazenamento e compressão (decidido em 02/11/2026)

Decisão do operador (02/11/2026), sobre as medições de [client-distribution-storage.md](client-distribution-storage.md): **zstd adaptativo, com o XOR dos `.hfs` desfeito, um objeto por arquivo**. É o menor tempo de download somado à descompressão em todas as velocidades até 300 Mbit/s (4.6 do estudo: 15,1 min a 100 Mbit/s contra 20,2 min com os `.hfs` como estão e 19,0 min com `.tar.gz`) e o mais barato de publicar (4.7: a Miri inteira em 6 s de compressão). Os arquivos não são escondidos nem cifrados: o que importa é a integridade (SHA-256 do arquivo final) e a autenticidade (manifesto assinado com Ed25519).

Do pw-universal ficam o manifesto completo e assinado por versão, os objetos por SHA-256 (cada conteúdo é baixado e guardado uma vez, mesmo que apareça em várias versões), a retomada com `Range`, a chave Ed25519 nascida no serviço e o fluxo rascunho → publicar → reverter. Os pacotes `.tar` de instalação do pw **não** são usados aqui: comprimem só ≈ 0,4 % melhor, dobrariam o armazenamento e exigiriam consolidar a instalação a cada versão grande.

1. **Objeto por arquivo, endereçado pelo SHA-256 do arquivo final no disco do jogador** (com o XOR). Vale para instalar, atualizar e reparar. "Verificar arquivos" não depende da transformação, e o mesmo conteúdo nunca é guardado duas vezes (a v3 reaproveita 2.666 dos 2.681 `.hfs` da v1).
2. **zstd adaptativo:** a publicação comprime cada arquivo com zstd 3 e só recomprime com zstd 19 se o resultado ficou abaixo de 97 % do original. Os `.comp` (zlib do próprio jogo: materiais, pacotes de classe) ficam no nível 3; mapas, scaleform, som, shaders, resource, modelos e os soltos vão a 19. Checksum de quadro ligado, janela padrão do nível (pico de 9 MB para descomprimir, seguro num Windows 7 de 32 bits), **sem `--long`**. O launcher descomprime qualquer nível com o mesmo código.
3. **`transform: hfs-xor`** em todos os `.hfs`, exceto o índice `E608DF10….hfs`: o servidor guarda o arquivo inteiro com o XOR desfeito (seção 2.4; desfazer só nas regiões cifradas dá o mesmo tamanho). O launcher descomprime, refaz o XOR em fluxo pela posição absoluta e confere o SHA-256. A tabela de 4.096 bytes vai como objeto do próprio manifesto (`hfs-keystream`), fora do Git. Ganho medido: mapas de 57,6 % para 27,8 % do tamanho, shaders de 42,9 % para 0,8 %.
4. **Delta binário entre versões** (`--patch-from` sobre a forma clara, antigo e novo até 64 MB, memória de aplicação ≤ 128 MB): gerado ao publicar para cada arquivo que mudou de N−1 para N, se ficar abaixo de 50 % do objeto. Na prática: `sql/heroes.db3`, os três DLLs e os `.hfs` refeitos com arquivos armazenados (um pacote refeito: 187 KB contra 14,1 MB sem desfazer o XOR); o índice vai inteiro. O launcher usa o delta quando tem o SHA antigo e encadeia versões; senão baixa o objeto. "Verificar arquivos" nunca usa delta.
5. **Arquivos do jogador** (`cfg/config.cfg`, `SAVE/`, opções): marcados `preservar`. São instalados se faltarem e nunca conferidos nem sobrescritos.
6. **Exclusões da v1** (lista inicial, decisão D-L3): `hfs_extracted/`, `lab-backup/`, `l0-*`, `*.bak`, `*.pre-*.bak`, logs (`*.log`, `npp_*_std*.log`, `fmod.log`), `__pycache__/`, `downloads/`, `DownloadLists/`, `passport/` (atualizador Python da Nexon), `BlackCipher/`, `NMService.exe`, `_eu_AdBalloonExt.exe`, `VindictusLauncher.exe`, `bcdedit.exe`, `start*.bat`, `maps/graphs/*.ain`, `demoheader.tmp`, `hfs-keystream.bin` (vai como objeto do manifesto). **Acréscimos de 07/11/2026** (inventário das camadas; decisões do operador): `*.nexon`, `cfg/config_pendingkey_concmd.cfg` (liga `developer 1`), `bin/class-routing.json`, `sql/heroes.db3.pre-*`, `sql/heroes.db3.lab-items.json`, `nmcogame.ini` e `vindictus-launcher.json` (gerados pelo launcher), `vindictus-launcher.exe` (distribuído à parte) e `bin/config_material.txt` (opções de vídeo; a engine cria pela detecção do hardware: **hipótese** até a instalação limpa do L3). Preservar também `cfg/config_env.cfg`, `cfg/config_ex.cfg`, `cfg/language.cfg` e `cfg/config_<classe>_ex.cfg`. Os itens de teste do editor de itens (`fiona_inner_lab`, `fiona_inner_fringe`, `fiona_inner_zero`, `evy_inner_zero`, seus pacotes e textos) ficam fora das versões; as edições publicadas pelo painel entram.
7. **Leiaute do armazém** (`${CLIENT_DIST_DIR}`): `objects/<aa>/<sha256>.zst`, `deltas/<sha antigo>-<sha novo>.zst`, `manifests/<n>.json` + `.sig` (caminho, SHA-256, tamanho, `transform`, tamanho do objeto, `preservar`, deltas a partir de N−1), `versao.json` + `.sig` e `status.json` (dinâmico, não assinado). Sem `packs/`. Objetos nunca são apagados ao reverter; uma limpeza explícita no painel remove os que nenhum manifesto publicado cita. O registro das versões (número, título, notas, autor, estado, mínima, versão de conteúdo ligada) fica no PostgreSQL, numa migração nova, com auditoria do painel.
8. **Tamanhos esperados** (estudo, seção 6): instalar a v3 ≈ 10,96 GB de download (de 15,04 GB no disco); atualizar v1→v2 ≈ 7 MB e v2→v3 ≈ 1,82 GB; servidor ≈ 11 GB para v1+v2+v3; importar a base ≈ 37 min numa thread (metade com duas).

### 4.4 Login pelo launcher e "Start Game" direto para a seleção

Fluxo alvo:

1. O launcher pede login e senha, os mesmos do painel. `POST /api/launcher/login` (no listener do painel; HTTPS na publicação externa) usa o mesmo `authenticate()` do painel (argon2, limite por IP e por conta, bloqueio, auditoria `launcher.login`), vale para qualquer conta ativa e abre uma **sessão do launcher** (token Bearer, só o SHA-256 em `launcher_sessions`, migração 0052), sem cookie e sem acesso ao painel. A sessão dura até o launcher fechar (`POST /api/launcher/logout`), a senha mudar ou a conta ser desativada, ou no máximo 12 horas se o launcher morrer (decisão do operador, 02/11/2026: o login vale até fechar o launcher). A cada Jogar, `POST /api/launcher/ticket` (Bearer) devolve um ticket `lt` + 22 dígitos base36 minúsculos (24 caracteres, cerca de 113 bits), de uso único, que vale enquanto a sessão durar (`game_launcher_tickets`, migrações 0051/0052). Senha errada: 401 genérico. Nenhuma senha em disco; o launcher lembra só o login. **Feito em 02/11/2026** (`src/application/admin_session.rs`, `src/http/admin.rs`).
2. O launcher abre `Vindictus.exe` com os argumentos de hoje mais `-launcher_ticket <ticket>`.
3. Na tela inicial, "Start Game" não abre o diálogo de login: o cliente envia `UserLoginMessage` com o ticket no campo `passport`.
4. O `lab_frontend` reconhece o formato do ticket e o gasta (`game_links::redeem_launcher_ticket`: ticket não usado, sessão aberta e não vencida, conta ativa, desbloqueada e com a mesma senha da sessão; `RETURNING` o nome de jogo da conta). Um ticket que não resgata é recusado, nunca lido como nome digitado. A identidade é a mesma do login por nome (nome de jogo da conta), mantendo os UIDs. Seleção de personagem e segunda senha seguem iguais. **Feito em 02/11/2026.** **Revisto em 03/11/2026 (LA4):** "Go Back" na seleção de personagem faz logout na mesma conexão, e o Start Game seguinte manda o mesmo ticket da linha de comando; gasto, ele era recusado (`GAMEUI_LOGIN_FAIL_PERMISSION_FAIL`, "We are currently in the Premium Open period"). Agora o primeiro login amarra o ticket ao endereço dele (`redeemed_from`, migração 0053), e o mesmo jogo entra de novo com ele enquanto a sessão do launcher durar, só desse endereço; o Jogar seguinte, o logout ou o fim da sessão o aposentam.
5. **Feito em 07/11/2026 (D-L6):** o login por nome digitado (login de conta ou nome da lista permitida) só vale com `typed_login: true` no perfil privado do laboratório (`lab_runtime_config.rs`; `prepare-lab-frontend-profile.ps1 -TypedLogin`). Sem o campo, o jogo aceita só o ticket do launcher, o que fecha a falha de entrar sabendo só o login.

Como o cliente recebe o ticket (etapa L-A; evidência na seção 4.1):

- **Escolhido:** `patch_client_launcher_login.py` (seção `.hlgn` no `client.dll`, na cadeia de `docs/client-dll-patches.md`) e `-launcher_ticket <ticket>` na linha de comando, lido por `CommandLine()`. Aplicado na cópia de laboratório em 02/11/2026 (`c0b5d416…` → `0b7d0248…`). O ticket fica visível na linha de comando para processos do mesmo usuário; por isso é de uso único e morre com a sessão do launcher.
- **O diálogo de login pode piscar** por um instante: o stub dispara a transição no mesmo `OnShow` que o abre.
- **Limite conhecido:** depois de um login recusado ou de voltar ao título, o próximo Start Game repete o mesmo ticket, já usado, e é recusado; o jogador abre o jogo de novo pelo launcher (no laboratório, pode digitar o login na página).
- **Não usados:** `nexon_api.dll` próprio (o jogo não pega a sessão por ele; fica como opção para extras, por exemplo presença no Discord), `-mantis` (exigiria emular o NXL e entender o estado `0x29`), o ConVar `event_account` (o Start Game só o lê nos modos de evento), `AutoLogin.txt` (exige o diálogo aberto) e o launcher digitar no diálogo (Scaleform, sem controles Win32).
- **Teste de cliente LA1** (`docs/client-tests/L-launcher.md`): `-launcher_ticket admin` → Start Game → seleção de personagem sem o diálogo; sem o parâmetro → diálogo como antes; conta inexistente → recusa. No L4, com ticket: ticket reutilizado ou vencido → recusa.

### 4.5 Status dos serviços

- O `updates` monta o `status.json` a cada 10 s, sondando pela rede interna do Docker: `server` (`/health/ready`) e o processo `game` (rota interna nova `/internal/status`: frontend 27015, canal 27003, relay 27005, manutenção agendada do B4.4c, jogadores conectados, versão de conteúdo publicada).
- Sem montar o `docker.sock` (daria controle total do Docker a um serviço exposto) e sem conectar no 27015 (abriria uma sessão de login; o healthcheck atual evita isso de propósito).
- O `status.json` leva também os endereços do painel e do cadastro aberto e as notícias publicadas pelo painel.

### 4.6 Launcher (Windows 7 em diante)

**Primeira versão feita em 03/11/2026 (decisão do operador: Rust + Win32):** `tools/launcher/` (pacote à parte, `[workspace]` próprio, fora do Docker). Janela Win32 com login e senha, sessão do launcher, Jogar (pede o ticket e abre o `Vindictus.exe` com `-launcher_ticket`, espera o jogo fechar), Sair, pasta do jogo (detecta a pasta do exe; `SHBrowseForFolderW`), status do servidor a cada 30 s, botões Painel e Criar conta (abre `/login?cadastro=1`), campo do servidor e `vindictus-launcher.json` ao lado do exe (servidor, pasta, último login; nunca senha, sessão ou ticket). Fechar o launcher faz logout (com o jogo aberto, pergunta antes). `build.ps1` gera o exe de 32 bits `i686-win7-windows-msvc` (1,37 MB; importa só kernel32, user32, gdi32, comctl32, shell32, ole32, bcrypt, ws2_32, ntdll e advapi32, sem função exclusiva do Windows 10). Único módulo com `unsafe`: `src/ui.rs` (chamadas Win32); `#![deny(unsafe_code)]` no resto. Instalar, atualizar e verificar arquivos entram com o L1–L3, na mesma janela. **Administrador (LA4, 03/11/2026):** o `Vindictus.exe` do 1.69 declara `requireAdministrator` no manifesto, então um launcher sem elevação não conseguia abri-lo. O launcher abre o jogo com `__COMPAT_LAYER=RunAsInvoker` (camada do próprio Windows desde o Vista: ignora o pedido e roda com as permissões do usuário, sem UAC e sem mudar o exe); a caixa "Abrir o jogo como administrador" (`game_as_admin` no json) usa `ShellExecuteExW` com `runas`, pedindo o UAC só para o jogo. Se o jogo funcionar sem administrador (LA5), o padrão fica; senão, o modo elevado.

- **Mesma solução do `pw-launcher` B275**, que o operador já confirmou num Windows 7 real: Rust com janela Win32 nativa (`windows-sys` 0.52, sem Tauri/WebView2), alvo `i686-win7-windows-msvc` (32 bits: roda no 7 de 32 e 64 bits e no 10/11), `-Zbuild-std=std` com `RUSTC_BOOTSTRAP=1`, CRT estático (sem depender do KB2999226), manifesto com `supportedOS` 7–10, comctl32 v6 e `dpiAware`. Conferir a tabela de importações a cada build (só funções do Windows 7).
- **Rede:** `ureq` com rustls e raízes embutidas (`webpki-roots`), porque o SChannel e o repositório de certificados do Windows 7 costumam estar desatualizados. O pw nunca testou HTTPS no 7; fica no gate.
- **Tela única:** notícias; status do servidor (online, manutenção com horário de volta); versão local × publicada; barra de progresso; login, senha e "Entrar"; botões "Jogar", "Verificar arquivos", "Painel", "Criar conta" e pasta do jogo. Sem cliente: "Baixar o jogo" ou "Já tenho o cliente" (confere e baixa só a diferença). Desatualizado: atualiza ao abrir. Em manutenção: "Jogar" desabilitado.
- **Estado** em `<pasta do jogo>/.vindictus-update/`: `estado.json`, manifesto aplicado, parciais retomáveis e um diário de aplicação, para retomar uma atualização interrompida.
- **Atualizar:** `versao.json` + assinatura → Ed25519 com a chave embutida → manifesto alvo (assinado) → diferença com o manifesto local → deltas/objetos na pasta de preparo → SHA-256 → aplicar com o jogo fechado (`.novo` + rename) → gravar o estado. Antes de jogar, conferência rápida (tamanho e data contra o estado); "Verificar arquivos" confere o SHA-256 de tudo e repara.
- **Autoatualização:** o `versao.json` traz versão, SHA-256 e objeto do launcher; ele baixa, confere, renomeia o exe atual para `.old` e reinicia.
- **No projeto:** `tools/launcher/` (código, ícone, `.rc`, manifesto, `build.ps1`) e a chave pública em `tools/launcher/update-public-key.txt`, gerada pelo `updates` na primeira execução. A privada nunca sai do servidor. O endereço do servidor fica em `launcher.json` ao lado do exe.

### 4.7 Versões, receitas e publicação

- **Camadas** (decisão do operador de 07/11/2026, "camadas reconstruídas"): **v1** = 1.69 EU + tudo que não é classe nova (`Mss32.dll` bom, IOCP do `engine.dll`, limite da loja e login do launcher no `client.dll`, `nmcogame.dll` do Messenger, EndPoint, valores originais e metas de história no `heroes.db3`, conteúdo B1–B5, collabs e ícones Fairy Tail, edições publicadas pelo painel); **v2** = v1 + Delia (classe 10); **v3** = v2 + Miri (classe 11, assets do NA). Os itens de teste do editor (`fiona_inner_lab`, `fiona_inner_fringe`, `fiona_inner_zero`, `evy_inner_zero`) ficam fora das três; os números de costume deles continuam reservados, então a Miri mantém no cliente os números que o servidor dá aos itens dela.
- **Receita** (`scripts/client/build_client_version.py --version 1|2|3 --out .cache/client-versions/v<N>`, 07/11/2026): numa pasta nova, copia o original somente leitura sem as exclusões (item 6 de 4.3), aplica as cadeias de DLL da camada (`docs/client-dll-patches.md`, "Versões distribuídas em camadas", com os hashes conferidos), recupera o `Mss32.dll` (`recover_mss32.py`), junta o `nmcogame.dll` compilado (`tools/nmcogame/build.ps1`), prepara o `heroes.db3` (EndPoint, `apply_original_content.py`, `align_story_goals.py`), põe o filme de criação da Delia (`apply_delia_creation_movie.py`, v2+) e roda `apply_lab_content_additions.apply` com a camada (`--classes`) e os itens de teste excluídos; o `player_costume.txt` de referência vem do pacote original, não da extração do laboratório. No fim apaga as sobras da montagem (*backups*, `lab-backup/`) e grava `<pasta>.report.json`: SHA-256 e tamanho de cada arquivo, os que diferem do original, as marcas `preserve` (arquivos do jogador) e o resultado de cada passo. `--link-from <versão anterior>` troca, depois da montagem, cada arquivo igual ao da versão anterior por um *hard link* somente leitura (três versões ocupam ≈ 16 GB em vez de ≈ 42 GB; uma escrita posterior falha em vez de mudar as duas). As três versões saem do mesmo *commit*; `git archive <ref> scripts/client scripts/content` numa pasta temporária só é preciso para refazer uma versão já publicada com código antigo (não `git worktree`, por causa da junction `.cache/play-client`).
- **Conferência** (`scripts/client/compare_client_version.py`): `--reference .cache/play-client` compara cada arquivo distribuído byte a byte e só aceita as diferenças explicadas pelos itens de teste (os pacotes deles; as linhas deles no `heroes.db3`, nos pacotes de texto e no `player_costume.txt`; o índice) e os arquivos do jogador; `--inventory .cache/verification/client-versions/inventory.json` confere que os arquivos alterados de cada versão são as camadas do inventário menos os pacotes dos itens de teste.
- **Importar a base** (uma vez por servidor): copiar o cliente original para uma pasta do servidor (robocopy ou scp) e rodar a importação no contêiner (`client-dist import --source /import/1.69 --exclude docker/client-dist/exclude-v1.txt`). Enviar mais de 10 GB pelo navegador não é recomendado; o painel mostra o progresso e aceita arquivos avulsos num rascunho, como os "itens por caminho" do pw.
- **Publicar** (`client-dist publish --tree <preparo> --title … --notes …`, ou o painel): calcula os SHA-256, envia só o que o armazém não tem (`POST /internal/objects/missing` devolve o que falta; envio retomável), gera os deltas contra a versão anterior, grava e assina o manifesto e troca o `versao.json`. Num servidor remoto, o mesmo comando usa a API administrativa autenticada por HTTPS.
- **Página "Versões do cliente"** no painel: lista, notas (aparecem no launcher), publicar rascunho, definir a mínima, retirar (reverter publica N+1 igual a N−1; objetos nunca são apagados), limpar objetos sem uso, uso de disco e notícias. Tudo vai para a auditoria do B4.
- **Conteúdo do servidor:** a publicação com manutenção (B4.4c) que toca o cliente gera a versão N+1 (o `heroes.db3` passa a ser gerado no servidor, substituindo o `start-lab.bat`), e o servidor só sai da manutenção quando ela existir. O protocolo não leva a versão do cliente; o login do launcher só emite ticket se ele declarar versão ≥ mínima. A declaração não prova nada, mas evita jogar desatualizado por engano.

### 4.8 Segurança

- Ticket só como hash, uso único, 2 minutos, nunca em log. Limite de tentativas no login do launcher, como no painel.
- API interna do `updates` só na rede do Docker e com segredo. Na publicação externa, HTTPS por proxy reverso (por exemplo Caddy com Let's Encrypt).
- Nenhum caminho fora da pasta do jogo (recusar `..`, absolutos, links, nomes reservados do Windows); limites de tamanho por manifesto e por objeto; nunca executar arquivo baixado sem hash conferido; autoatualização assinada; nenhuma credencial em log.
